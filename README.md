# dipper-timing

**Timing-leakage assessment of Dipper software implementations on x86, ESP32 and FIT IoT-LAB boards.**

This repository tests whether the table-based C implementations of the Dipper-64/128 block cipher have execution time that depends on the key or the data. It runs on eleven platforms whose memory systems range from no cache, through small flash caches, to full CPU data caches. It also measures what a constant-time implementation costs.

Verdicts are in [`RESULTS.md`](RESULTS.md), the platform details in [`ENVIRONMENT.md`](ENVIRONMENT.md), and the progress log in [`STATUS.md`](STATUS.md). Every number comes from code that was run. The raw logs are in `results/raw/`.

## Implementations (`impl/`)

| variant | file | what it is |
|---|---|---|
| `small` | `dipper.c` | upstream, unchanged: 16 B S-box table indexed by secret nibbles, bit loop over the public permutation table |
| `fast` | `dipper_fast.c` | upstream, unchanged: 512 B two-nibble S-box and 2 KB nibble-scatter permutation tables, built at run time in RAM |
| `fast_const` | `dipper_fast_const.c` | `fast` with the same tables as precomputed `const` arrays (flash on MCUs), generated by `gen_tables.py` and checked byte-identical by `check_tables.c` |
| `ct` | `dipper_ct.c` | new constant-time version: GIFT S-box as a Boolean formula on bit planes, permutation as 25 fixed mask/shift pairs (`ct_perm.h`, generated), same formula in the key schedule |
| `leaky` | `dipper_leaky.c` | **positive control, deliberately leaky**: `small` plus a branch on one secret bit that adds a dummy loop |

The upstream source is Dipper-lightweight-cipher at `3ae6788` (`timing/`); see `impl/SOURCE.md`. `fast` and `fast_const` use the key schedule of `small`, as in the upstream repository.

## Method (`common/dudect.c`)

The test is dudect-style (Reparaz, Balasch, Verbauwhede, DATE 2017).

- **Inputs.** Each measurement is randomly assigned to one of two classes.
  - Test A: fixed key; class 0 uses a fixed plaintext and class 1 a random plaintext.
  - Test B: fixed plaintext; class 0 uses a fixed key and class 1 a random key. The key schedule is inside the timed region.
- **Statistics, computed on the device.**
  - Welford mean and variance per class, and the Welch t-test.
  - Tests: no crop, 10 crop levels p_k = 1 − 0.5^k, and a second-order test.
  - The reported value is the maximum |t| over all tests.
- **Thresholds.** 4.5 (TVLA) and 10 (dudect).
- **Repetition.** A leak is reported only if it repeats in an independent run with a new seed, on another node or CPU.
- **Raw dump.** The first 131072 samples of every run are printed. The host recomputes t from them and compares the result with the device value to the last bit.

## Reproduce

Requirements: Python 3, and for the boards the toolchains listed in `ENVIRONMENT.md`.

**Correctness (any host).** The first command checks that the tables match; `dudect_host` prints the self-test: TV1–TV4 for all variants, plus `ct` and the others against `small` on random inputs.
```bash
cc -O2 -o check_tables impl/check_tables.c && ./check_tables
make -C harness/posix && harness/posix/dudect_host -n 0
```

**x86-64 Linux.** The script runs seed 1 on CPU 3 and seed 2 on CPU 6, with N = 10^6. The `ctgrind` script runs the Valgrind memcheck check.
```bash
make -C harness/posix
harness/posix/run_x86.sh
harness/ctgrind/run_ctgrind.sh
```
For the extra x86 runs, use `harness/posix/dudect_host -s 3 -n 10000000 -r 131072 -p 3` (and `-s 4 … -p 6`).

**Linux ARM board (IoT-LAB a8).** Copy the repository to `~/shared` on the frontend, then on the node run:
```bash
make -C harness/posix
harness/posix/dudect_host -s 1 -n 1000000 -r 131072 -p 0
```

**ESP32 (own board, USB).** This uses PlatformIO in a local venv. The `pio run` env can be `nodemcu32s` (seed 1), `nodemcu32s_s2` (seed 2) or `nodemcu32s_wifi` (seed 3, Wi-Fi scan load).
```bash
python3 -m venv .venv && .venv/bin/pip install platformio==6.1.18
cd firmware/esp-idf
../../.venv/bin/pio run -e nodemcu32s -t upload --upload-port /dev/cu.usbserial-0001
cd ../..
.venv/bin/python scripts/esp/capture.py /dev/cu.usbserial-0001 results/raw/esp32_s1_nodemcu32s-wifioff_<UTC>.log nodemcu32s
```

**IoT-LAB Cortex-M (RIOT).** Build on the Grenoble frontend, after `iotlab-auth` there:
```bash
scripts/iotlab/sync.sh grenoble
scripts/iotlab/build_riot.sh iotlab-m3 bin-s1 SEED=1
```
The board can be `iotlab-m3`, `samr21-xpro`, `nrf52840dk`, `b-l475e-iot01a` or `rpi-pico`. Then submit, flash and start the detached capture:
```bash
ssh <login>@grenoble.iot-lab.info 'iotlab-experiment submit -n dt -d 600 -l saclay,samr21,3+12'
scripts/iotlab/sync.sh saclay
scripts/iotlab/start_run.sh <exp_id> samr21-3.saclay dipper-timing/firmware/riot/bin-s1/samr21-xpro/dipper-timing.elf samr21_s1
scripts/iotlab/collect.sh saclay
```

**IoT-LAB ESP32-C6 / LoPy4.** These boards cannot be flashed when the experiment starts. Build with `pio run -e esp32c6` (or `lopy4`), merge the image into one `.bin` at 0x0 with esptool `merge_bin` (offsets in `.pio/build/<env>/flasher_args.json`), submit without firmware, then run `start_run.sh` with the `.bin`.

**Analysis.** `make analysis` runs the whole chain below, and `make paper-zip` packs `paper/` for Overleaf.
```bash
python3 analysis/recompute.py results/raw/*.log
python3 analysis/summarize.py
python3 analysis/footprint.py
python3 analysis/ct_asm_scan.py results/raw/asm/*.txt
```
- `recompute.py` recomputes t from the raw dumps and compares it with the device values.
- `summarize.py` writes the tables in `results/summary/` and the verdicts.
- `footprint.py` gives code and table sizes from `results/raw/nm/`.
- `ct_asm_scan.py` lists the branches and memory accesses of `ct`; see `docs/ct_asm_review.md`.

## Layout

```
impl/            five variants, table generator, upstream source record
common/          dudect core (platform-independent), PRNG
harness/posix/   x86-64 / Linux-ARM / macOS test program, timer probe
harness/ctgrind/ Valgrind memcheck (ctgrind-style) static check
firmware/riot/   one RIOT app for all Cortex-M boards
firmware/esp-idf/ one ESP-IDF app for ESP32 and ESP32-C6
scripts/iotlab/  sync / build / start / capture / collect
scripts/esp/     USB serial capture for the own ESP32 board
analysis/        recompute, summary tables, footprint, assembly scan
results/raw/     raw logs (one per run), ctgrind logs, disassembly, nm
results/summary/ CSV and Markdown tables
docs/            research notes, ct assembly review
paper/           JMTE manuscript (paper.tex), generated tables, figures
Makefile         analysis pipeline, host build, Overleaf zip
```
